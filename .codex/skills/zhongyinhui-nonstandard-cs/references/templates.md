# 中隐会 CS 非标问题交付模板

## 信息不足时的追问输出

当信息不足时，先输出给 CS 的追问清单：

````markdown
## 需要向客户补充确认的信息

为了判断这个需求能否落地，建议先确认以下信息：

1. 具体业务场景：这个能力最终用于哪个流程或岗位？
2. 目标结果：客户希望产出什么，成功标准是什么？
3. 数据规模：一次处理多少数据，多久处理一次，是否有并发要求？
4. 现有基础：客户现在使用哪些系统、工具、账号、素材或 API？
5. 交付边界：客户是要一份方案，还是希望有人实际开发落地？
6. 预算周期：希望多久上线，可接受的工具或 API 成本是多少？
7. 风险限制：是否涉及隐私数据、敏感行业、合规审批或准确率硬指标？
````

## 《技术路线与执行方案》

用于绿灯或黄灯需求。黄灯需求必须明确依赖条件和边界。该内容是客户 PDF 正文，不要包含 CS 沟通话术，不要包含代码。

````markdown
# 《{客户需求简称}》技术路线与执行方案

## 1. 需求本质抽象

客户提出的需求，本质上是：{用一句话说明技术本质}。

当前判断：{绿灯/黄灯}。

推荐结论：{建议直接尝试 / 建议小范围验证 / 建议分阶段推进}。

## 2. 推荐技术路线

建议采用：{脚本/API/SaaS/开源工具/自动化流程/组合方案}。

核心流程：

1. {步骤一}
2. {步骤二}
3. {步骤三}
4. {输出或验收方式}

## 3. 执行方案

### 方案 A：最小可行版本

- 目标：{先跑通什么}
- 所需条件：{账号、数据、素材、权限、环境}
- 预估周期：{粗略周期}
- 适合场景：{适合什么规模或业务}

### 方案 B：增强版本

- 目标：{增强能力}
- 所需条件：{工程、预算、系统集成、运维}
- 适合场景：{更高并发、更多数据、正式生产}

## 4. 执行路径

- 第一阶段：{演示版或小样本验证怎么做}
- 第二阶段：{扩大范围或自动化流程怎么做}
- 第三阶段：{长期稳定运行或系统化建设怎么做}

## 5. 成本、限制与风险

- 成本：{API、工具、服务器、人工成本}
- 限制：{并发、速率、文件大小、账号权限、数据质量}
- 风险：{稳定性、隐私、安全、合规、幻觉、人工复核}

## 6. 建议下一步

建议先用 {小样本/单流程/测试账号} 做一次验证。验证通过后，再决定是否进入正式部署或扩大规模。
````

PDF 生成要求：

- 绿灯或黄灯时，将上方客户正文保存到当前项目工作目录下的 `outputs/zhongyinhui-nonstandard-cs/{客户需求简称}.md`。
- 使用 `scripts/render_deliverable_pdf.py outputs/zhongyinhui-nonstandard-cs/{客户需求简称}.md outputs/zhongyinhui-nonstandard-cs/{客户需求简称}.pdf` 生成 PDF。
- PDF 只包含客户交付正文，不包含下面的 CS 沟通话术和内部备注。
- PDF 使用普通 A4 文档说明风格：标题、摘要表、分节标题、段落和列表即可；不要追求复杂封面、重色块或卡片化排版，避免文字与线条重叠。
- 如果需要做渲染检查，可临时导出页面截图；检查完成后删除临时截图，不要把测试产物留在项目根目录。
- `outputs/zhongyinhui-nonstandard-cs/` 只保留最终 Markdown 和最终 PDF；不要保存预览截图、旧版 PDF 或缓存文件。

## 《技术可行性与前瞻评估报告》

用于红灯需求。重点是让客户觉得被认真对待，并获得战略价值。

````markdown
# 《{客户需求简称}》技术可行性与前瞻评估报告

## 1. 需求本质与当前瓶颈

客户提出的需求，本质上是：{用一句话说明技术本质}。

当前判断：红灯。

目前不建议直接投入落地，主要原因是：

1. {技术瓶颈}
2. {成本或 ROI 问题}
3. {数据、系统、合规或准确率风险}

## 2. 如果坚持自建，需要的技术栈与团队

### 技术栈

- {模型/API/框架}
- {数据处理/向量库/工作流/后端/前端/运维}
- {监控、权限、安全、评测体系}

### 团队配置

- {算法/后端/数据/产品/运维/测试/合规角色}

### 成本结构

- 一次性建设成本：{范围}
- 持续运行成本：{范围}
- 隐性成本：{数据清洗、评测、人工审核、系统维护}

## 3. 避坑指南

行业里做类似项目时，常见问题包括：

1. {坑一：例如错把知识库当智能体、忽视数据质量}
2. {坑二：例如准确率承诺过高、没有人工复核}
3. {坑三：例如只做演示不做运维、并发成本失控}

## 4. 3-6 个月技术前瞻

未来 3-6 个月，可能出现的低成本解法包括：

- {模型能力、长上下文、工具调用、视觉能力、自动化平台、价格变化}
- {客户现在应该先准备的数据、流程或系统基础}

## 5. 当前建议

建议客户现在先做：{数据资产化/流程梳理/小范围验证/等待技术成熟/选择低成本替代方案}。

不建议现在做：{高成本训练、重度私有化、一次性大规模开发等}
````

## CS 沟通话术

沟通话术必须单独输出，作为 CS 可复制发送的内容。不要放进客户 PDF 正文里。

### 绿灯或黄灯

````markdown
关于您提到的需求，我们已经做了一次技术路线拆解，并整理成《技术路线与执行方案》。里面包含推荐实现方式、执行步骤、成本限制和风险提示。建议先用小样本跑一次验证，确认效果后再扩大规模。
````

### 红灯

````markdown
关于您提到的需求，我们做了一次深度技术推演，并整理成《技术可行性与前瞻评估报告》。目前直接落地的成本和风险较高，但报告里拆解了如果自建需要什么团队和技术栈、常见坑在哪里，以及未来半年可能出现的更低成本解法，方便您做战略判断。
````

## 内部备注

这些内容只能给 CS 或内部团队看，不要直接发给客户：

- 技能判定依据和内部风险分级。
- "由 Codex 生成"或类似表述。
- 未经核实的价格、平台能力、API 参数、模型发布日期。
- 对客户行业合规性的确定性承诺。
- 中隐会会负责定制开发、长期运维或结果兜底的承诺。
