# 客户需求与交付拆解分析

本 skill 是客户成功场景的中颗粒业务动作，不是完整客户成功 Harness。它负责把一份原始逐字稿或沟通记录拆成可跟进的需求、交付物、承诺、风险和画像增量，并给出写回建议。默认只产出分析包，不自动改客户档案、不自动写 CSV、不自动同步飞书。

## 适用边界

- 使用于用户提供客户逐字稿、会议纪要、聊天记录、录音转写或沟通材料，并要求做需求分析、交付拆解、客户画像建模、跟进建议、承诺审计或风险识别时。
- 不使用于只做资料入库、只维护 CSV、只同步飞书、只写正式交付物正文、只做销售分流或完整客户成功闭环时。
- 如果用户明确要求“入库”“更新档案”“同步飞书”“按完整客户系统执行”，先说明会进入更完整流程，再遵循当前仓库或项目的总规则。
- 如果用户只上传 `.mp3`、`.wav`、`.m4a` 等原始音频，先调用合适的转写流程拿到文本，再进入本 skill；本 skill 第一版不内置音频转写脚本。

## 触发与反触发

- 触发句示例：`帮我分析这份客户逐字稿`、`拆一下客户需求和交付`、`看这次聊完客户要做什么`、`建模客户画像增量`、`审计一下我们承诺了什么`。
- 反触发句示例：`先别分析，只归档`、`只同步飞书`、`只更新 CSV`、`直接写正式交付文档`、`做完整客户成功闭环`。
- 用户说法模糊但材料明显是客户沟通记录时，优先输出轻量分析包；不要直接进入全量写回流程。

## 命名说明

- 使用 `customer-` 前缀，对齐客户成功现有 skill 命名。
- 使用 `requirement-delivery` 表示核心业务对象，避免 `demand` 这类不够自然的硬翻译。
- 使用 `analysis` 表示输出分析包，不表示自动写回、同步或完整 Harness。
- 目录名、frontmatter `name`、调用名保持一致：`customer-requirement-delivery-analysis`。

## 输入检查

1. 识别输入类型：逐字稿、会议纪要、聊天记录、客户资料包或历史档案。
2. 抽取基础信息：客户名、公司名、会议日期、会议主题、参与人、来源文件。
3. 如果客户名、日期或主题缺失但仍能分析，标为 `待确认` 后继续；只有缺少原始内容本身时才要求用户补充。
4. 如果用户提供旧画像、权益清单或需求台账，先读取再对比；如果没有，明确写“本次仅基于当前材料判断”。

## 分析流程

1. **证据切片**：给原始语料分段，保留说话人和关键原话。长逐字稿只摘取与需求、承诺、画像、风险相关的证据段。
2. **事实抽取**：只提取已发生事实、客户明确表达、我方明确回应、时间约束、资源约束、已有交付背景。
3. **需求拆解**：区分 `明确需求`、`隐含需求`、`待确认需求`、`非需求信息`。每条需求都写证据、优先级、状态和待确认点。
4. **权益或范围初判**：有权益清单时按清单判断 `范围内`、`疑似范围内`、`超范围`、`权益待确认`；没有清单时不要硬判，只列需要核验的信息。
5. **承诺审计**：只把我方明确说出的交付、时间、动作写成承诺。客户期待、销售设想、模糊口头意向不能写成我方承诺。
6. **交付拆解**：把需求拆成交付物、任务、验收口径、版本计划和依赖条件。智能体类交付物保持“一个逻辑交付物 + 多个版本记录”的思路。
7. **画像增量**：对客户沟通风格、决策偏好、交付偏好、风险敏感点、情绪价值需求做增量建模。变化类型只用 `新增`、`强化`、`修正`、`冲突`、`待确认`、`无变化`。
8. **风险与阻塞**：识别范围风险、过度承诺风险、资料缺口、权限风险、客户预期风险、交付成本风险。
9. **下一步动作**：输出跟进任务、客户待确认问题、内部待确认问题、建议话术或下一次会议检查清单。
10. **写回建议**：说明哪些内容建议写回长期画像、需求交付跟进、交付物版本记录、风险索引或飞书预览；除非用户明确要求，不执行真实写回。

## 状态字典

- 事实状态：`已确认`、`待确认`、`推断`。
- 需求类型：`明确需求`、`隐含需求`、`待确认需求`、`非需求信息`。
- 权益判断：`范围内`、`疑似范围内`、`超范围`、`权益待确认`、`不适用`。
- 需求状态：`新增`、`待确认`、`分析中`、`已转交付`、`暂缓`、`已关闭`。
- 交付状态：`待拆解`、`制作中`、`待客户反馈`、`需迭代`、`阶段通过`、`已完成`、`已暂停`。
- 画像变化：`新增`、`强化`、`修正`、`冲突`、`待确认`、`无变化`。
- 风险等级：`高`、`中`、`低`、`待确认`。

## 失败兜底

- 没有逐字稿或有效沟通内容：说明无法分析，并列出需要用户补充的最小材料。
- 客户身份不清：用 `客户待确认` 继续分析，不创建新档案。
- 旧画像缺失：只输出本次画像增量，不声称完成新旧对比。
- 权益清单缺失：权益判断统一标 `权益待确认` 或 `不适用`，不要猜测客户已购买权益。
- 证据冲突：保留冲突双方，标 `冲突` 或 `待确认`，不要强行合并成单一结论。
- 疑似敏感信息：只提示需要脱敏或权限确认，不把敏感信息扩散到可同步内容。

## 禁止动作

- 不覆盖原始逐字稿。
- 不把客户期待写成我方承诺。
- 不把低置信度推断写成事实。
- 不为每次沟通新建一份长期客户画像。
- 不默认写回客户档案、CSV、飞书或 Git。
- 不自动修改生产版 skill、SOP、话术或规则；只能生成修订建议，等待负责人确认。

## 黑灯和自进化预留

- 黑灯输入：待处理逐字稿目录、飞书表格新增记录或人工上传队列。
- 夜间动作：批量生成需求拆解、交付风险、待确认问题和次日跟进清单。
- 第二天输出：按客户聚合的需求和风险日报。
- 人工确认点：画像变化、权益范围、我方承诺、正式写回、同步飞书。
- 自进化回流：记录人工修改、客户反馈、交付结果和最终验收结论，生成下一版规则或 skill 变更建议。

## 完成检查

- 每条需求、承诺、画像变化和风险是否有证据或明确标 `待确认` / `推断`。
- 是否区分客户原话、AI 判断和我方承诺。
- 是否给出可执行的交付物、任务、责任人或待确认项。
- 是否说明写回建议而没有擅自真实写回。
- 是否留下可用于后续自进化的规则增量或人工确认点。
