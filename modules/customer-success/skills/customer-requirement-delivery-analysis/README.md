# customer-requirement-delivery-analysis

客户需求与交付拆解分析 skill，用于客户成功团队在每次客户沟通后，把逐字稿或会议记录拆成需求、交付物、承诺、风险和客户画像增量。

## 定位

这是一个中颗粒 Skill，不是完整客户成功 Harness。它适合白天人机协同使用：用户把客户逐字稿给 Codex，Codex 输出一份可审查、可写回、可进入下一步交付管理的分析包。

第一版不做自动入库、不做真实飞书同步、不改 CSV。后续如果要进入黑灯机制或完整客户成功流程，需要由 Harness 或总流程负责调度。

## 命名标准

- `customer-`：对齐客户成功部现有 skill 前缀。
- `requirement-delivery`：说明处理的是客户需求和交付拆解。
- `analysis`：说明第一版只生成分析包，不自动写回。
- 目录名、`SKILL.md` frontmatter `name`、调用名三者一致。

## 典型触发句

- 帮我分析这份客户逐字稿，拆一下需求和交付。
- 这次聊完客户之后，帮我建模客户画像，看看下一步交付什么。
- 从这份会议记录里找出客户需求、我方承诺和风险。
- 看看这次沟通有没有超范围承诺，以及要交付哪些东西。
- 用户上传 `.txt`、`.md`、`.docx` 格式的客户沟通记录，并要求分析需求或交付。

## 输入

- 必填：客户逐字稿、会议纪要、聊天记录、录音转写或上传的 `.txt`、`.md`、`.docx` 文本文件。
- 可选：旧客户画像、需求交付跟进台账、权益清单、历史交付记录、客户项目背景。
- 如果只有 `.mp3`、`.wav`、`.m4a` 等原始音频，先完成转写，再使用本 skill。

## 输出

- 证据切片
- 需求拆解表
- 权益或范围判断
- 承诺与交付拆解
- 任务清单
- 客户画像增量
- 风险与阻塞
- 待确认问题
- 写回建议
- 自进化回流建议

## 数据生命线原则

- 数据从客户原始沟通材料来，必要时读取旧画像和旧台账。
- 输出默认停留在对话或分析文档中，不直接覆盖生产数据。
- 涉及连续状态的对象必须留下状态字段，例如需求状态、交付状态、权益判断、画像变化类型。
- 所有低置信度信息必须标 `待确认` 或 `推断`。
- 人工确认后，才进入客户档案、CSV、飞书或下一版规则。

## 黑灯机制预留

未来可以扩展为夜间任务：自动扫描待处理逐字稿，第二天输出客户需求拆解、交付风险清单和待确认问题。但第一版只保留设计约束，不启用定时运行。

## 自进化预留

这个 skill 的输出结果可以收集人工修订、客户反馈、交付验收结果，用于生成下一版规则建议。AI 只能提出修订建议，不能自己偷偷修改生产版 skill。

## 评审重点

- 是否保持中颗粒边界，没有变成“客户成功全流程大杂烩”。
- 是否写清输入、输出、状态追踪、写回位置、人工确认点。
- 是否避免把客户期待误写成我方承诺。
- 是否避免在没有权益清单时硬判范围。
- 是否保留黑灯和自进化接口，但不默认自动执行。
